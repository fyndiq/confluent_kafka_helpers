# Migration Guide for v1

Migrating from `0.10` (`0.10.5`) to the latest `1.x` (`1.6.0`). 1.x releases are not tagged; versions are `setup.py` bumps on `master`.

## Required changes

- **OpenTracing is gone** (`1.0.0`): `extras_require['opentracing']`, `tracing.backends`, `tracing.tags`, and the null-tracer fallback are removed. Tracing always uses OpenTelemetry (`opentelemetry-api==1.27.0`).
- **`confluent-kafka[avro]==2.*`** (`1.0.2`): the `schema-registry` extra is dropped from this library's pin. Depend on `confluent-kafka[schema-registry]` yourself if you still need that extra.
- **`commit()` retries transient errors** (`1.2.0`): `REQUEST_TIMED_OUT` and `BROKER_NOT_AVAILABLE` are retried. No code change; commit can take longer under broker faults.
- **SIGTERM/SIGINT no longer exit immediately** (`1.3.0`): import sets a process-wide flag; `AvroConsumer` finishes the in-flight message and then leaves the loop. A second signal forces `sys.exit(0)`. Existing handlers are still invoked after the flag is set.

### Migration steps

1. Remove the OpenTracing extra and any imports of this library's OT API:

   ```text
   # Before (0.10)
   pip install confluent-kafka-helpers[opentracing]
   ```

   ```python
   # Before (0.10)
   from confluent_kafka_helpers.tracing import tags, tracer
   from confluent_kafka_helpers.tracing.backends.opentracer import OpenTracerBackend
   ```

   ```text
   # After (v1)
   pip install confluent-kafka-helpers
   ```

   ```python
   # After (v1) — only if you touch the tracer yourself
   from confluent_kafka_helpers.tracing import tracer
   from confluent_kafka_helpers.tracing import attributes as attrs
   ```

   Configure an OpenTelemetry `TracerProvider` in the app (or rely on your APM SDK). The library calls `trace.get_tracer`.

2. Treat SIGTERM/SIGINT as "stop after this message", not "exit now". Long handlers should poll the flag; raise Kubernetes `terminationGracePeriodSeconds` if a single message can exceed the default 30s:

   ```python
   from confluent_kafka_helpers import is_shutdown_requested

   for message in consumer:
       do_step_one(message)
       if is_shutdown_requested():
           break
       do_step_two(message)
   ```

   If another library's handler still calls `sys.exit`, import `confluent_kafka_helpers` *first* so its handler is the one installed, or accept that the other handler still exits immediately.

## Optional changes

- **Automatic header propagation** (`1.1.0`): set `headers.propagate` to a list of header keys on the consumer; the producer copies those values onto subsequent `produce` calls in the same context.
  The configured headers are also added to the related Kafka spans as
  `confluent_kafka_helpers.header.<header-name>` attributes.
  When `correlation_id` is configured for propagation, it is also recorded as
  the standard `messaging.message.conversation_id` attribute.

  ```python
  AvroConsumer({**config, 'headers.propagate': ['x-request-id']})
  ```

- **Default propagated headers** (`1.7.0`): `origin_action_type` and
  `action_started_at` are always included in the propagated header list. Services
  no longer need to add them to `headers.propagate`. Existing configs that list
  them still work; duplicates are ignored.
- **Producer OTEL service name** (`1.0.1`): produce spans set
  `confluent_kafka_helpers.producer.service.name` from `DD_SERVICE` / Datadog service name.
- **Consumer/producer use the package logger** (`1.1.2`): the underlying Confluent client is constructed with this library's structlog logger.

## Opt in to batch consumption

The new batch API is optional. Keep `AvroConsumer` for existing single-message
workers. For a batch worker, use `AvroBatchConsumer` instead of the experimental
`AvroConsumer.batches()` API. Replace `batch_max_size` / `batch_max_wait` config
keys with the `batch_size` / `timeout` constructor arguments, and remove
`poll_timeout`, `non_blocking` and custom `get_message` hooks from that worker.

### Handle, confirm output, then commit input

The following assumes the application's existing Kafka configs, `bulk_write`
and `build_event` functions. Output values must match the registered topic schema.

```python
from confluent_kafka_helpers.consumer import AvroBatchConsumer
from confluent_kafka_helpers.producer import AvroProducer

batch_config = {
    **consumer_config,
    "enable.auto.commit": False,
    "enable.auto.offset.store": False,
}
producer = AvroProducer(producer_config)

with AvroBatchConsumer(batch_config, batch_size=100, timeout=0.1) as consumer:
    for batch in consumer:
        with producer.delivery_scope(timeout=30.0):
            bulk_write([message.value for message in batch])
            producer.produce_many(
                {
                    "key": message._meta.key,
                    "value": build_event(message),
                    "source": message,
                }
                for message in batch
            )
        consumer.commit_batch(batch)
```

`batch_size` is a maximum, not a required batch length. Empty reads are skipped;
`timeout` bounds each native read in seconds. The batch consumer disables automatic
commits and offset storage, and rejects config that enables either.

`produce()` and `produce_many()` queue output. The delivery scope tracks all
publications on that producer, including ordinary calls from existing handlers.
It confirms delivery before successful exit and raises on enqueue, delivery or
callback failures, or unconfirmed output. Keep the commit **after** the scope;
do not catch a failure and then commit the batch anyway. Outside a scope,
`produce_many(timeout=...)` bounds queue waits but does not confirm delivery.

### Preserve each input's headers and trace

Use `source=message` for output collected after bulk processing. For existing
per-message handlers, activate the input's context explicitly:

```python
with producer.delivery_scope(timeout=30.0):
    for message in batch:
        with message.process():
            existing_handler(message)  # May call producer.produce() normally
consumer.commit_batch(batch)
```

`message.process()` activates that message's incoming trace and propagated
headers, then restores the previous context. A batch itself has a separate trace
linked to its inputs and no input's business headers. Explicit output headers
override propagated business headers. If batches exceed 128 messages, raise
`OTEL_SPAN_LINK_COUNT_LIMIT` to retain all input links.

### Ordering, failures and shutdown

- Preserve input order within each partition. `produce_many()` queues output in
  supplied order; Kafka does not provide global order across partitions
- `commit_batch()` commits the highest supplied offset plus one per partition.
  Only commit successful prefixes: a later offset also acknowledges earlier input
- Stop on fetch, processing, delivery or commit failure and allow uncommitted
  input to replay. Database writes and emitted events must be replay-safe;
  delivery confirmation does not make them atomic or exactly once
- The delivery timeout starts at scope entry. It bounds queue waits and output
  confirmation, not application or schema-registry calls. Keep batch handling
  within Kafka's `max.poll.interval.ms`
- Join worker threads and propagate their errors before leaving the scope. Enter
  `message.process()` inside each worker, preserve partition order, and do not
  share the producer with unrelated work or nest delivery scopes
- Reads stop on shutdown; records returned by a read interrupted by shutdown are
  left unprocessed. Applications scheduling their own work should check
  `is_shutdown_requested()` before starting queued handlers

Applications using eventsourcing helpers should normally use its managed
`consume_batch()` API instead; it owns output confirmation and input commits.
